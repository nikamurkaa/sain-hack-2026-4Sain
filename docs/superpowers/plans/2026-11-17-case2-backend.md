# Кейс № 2: план разработки «Номера, который знает гостя»

## Что мы делаем

Приложение подготавливает умный номер к отдыху конкретного гостя. Оно получает доступные сведения о его привычках, составляет расписание работы устройств на вечер, ночь и утро, а затем меняет настройки по просьбе гостя.

Например, гость предпочитает прохладу и мягкое пробуждение. Приложение учитывает эти предпочтения при подготовке номера. Если гость пишет «сделай теплее», оно меняет температуру, проверяет результат и показывает новое значение.

На хакатоне устройства представлены симулятором организаторов — сервисом, который принимает команды и хранит состояние виртуальной комнаты. Работающее решение должно действительно управлять этим симулятором. Одного изображения изменившейся температуры в интерфейсе недостаточно.

## Что уже готово

Инфраструктурная часть настроена:

- создан приватный репозиторий команды;
- настроен автоматический деплой из ветки main на выданный стенд;
- сервер запускается, проверка доступности работает;
- ключ доступа к стенду хранится в секретах GitHub;
- после деплоя автоматически проверяется запуск новой версии.

Адрес стенда: https://team25.hack.be-healthy.tech.

В рабочей ветке feature/case2-backend уже написаны серверная логика, подключение симулятора, /run и API интерфейса. Автоматические тесты и отдельная проверка настоящего симулятора выполнены. Полная проверка с моделью ещё не завершена, интерфейс разрабатывается отдельно. В main пока остаётся стартовый сервер. Актуальные результаты: [отчёт о проверках](../../verification.md).

## Как должно работать приложение

1. Приложение получает данные гостя и сведения о его проживании.
2. Определяет предпочтения по профилю и доступной истории: время сна, температуру, освещение, звуки и способ пробуждения.
3. Составляет расписание настроек на вечер, ночь и утро с учётом правил кейса и возможностей устройств.
4. Передаёт расписание в симулятор комнаты.
5. Показывает гостю подготовленные настройки и объясняет, на чём они основаны.
6. Принимает просьбу гостя, например «потише» или «разбуди на полчаса позже».
7. Проверяет допустимость изменения, выполняет его и получает фактическое состояние комнаты.
8. Сообщает результат. Если выполнить просьбу не удалось, показывает понятную ошибку.

Для автоматической проверки организаторов используется тот же код подготовки номера и обработки просьб. Отдельно реализуется /run — маршрут, через который проверяющая система запускает обработку набора заданий.

## Что нужно сделать на сервере

### 1. Подключить данные организаторов

Получать набор данных через API хакатона. API — это способ, которым наше приложение обращается к сервисам организаторов.

Набор загружается один раз на проверочный прогон. Затем сервер выбирает из него сведения о нужном госте, его историю и конкретное проживание или просьбу.

Нужно обеспечить:

- использование токена из входящего проверочного запроса;
- разделение данных разных гостей;
- обработку ошибок доступа и временной недоступности сервиса;
- исключение эталонных ответов из данных, на основании которых принимаются решения.

**Готово, когда:** сервер получает набор и корректно находит данные каждого гостя, не смешивая их между собой.

### 2. Определять предпочтения гостя

Собрать из профиля и истории настройки, которые нужны для подготовки номера. Для каждого выбранного значения сохранять источник: например, поле профиля или предыдущую просьбу.

Учитывать только сведения, известные к моменту обрабатываемого события. Более поздние сообщения использовать нельзя.

Отдельно различать постоянное предпочтение и разовую просьбу. Фраза «сегодня разбуди раньше» сама по себе не должна менять обычное время подъёма на все следующие проживания.

Павел описывает порядок выбора при противоречиях и поведение при нехватке данных. Николь реализует эти правила.

**Готово, когда:** для каждой настройки можно объяснить, откуда она взялась, а отсутствующие данные обрабатываются по заранее описанному правилу.

### 3. Составлять расписание номера

На основании предпочтений, времени проживания и правил кейса формировать расписание для:

- света;
- температуры;
- звука;
- штор;
- будильника;
- режима «Не беспокоить».

Расписание должно учитывать все правила R1–R8 из материалов организаторов. Числовые ограничения и временные интервалы берём из этих правил и схем устройств.

Отдельно проверить переход через полночь, часовые пояса, позднее заселение, отсутствие любимого звука и выключение звука после завершения воспроизведения.

**Готово, когда:** для проживания создаётся допустимое расписание, которое выполняет правила кейса и принимается симулятором.

### 4. Обрабатывать просьбы гостя

Поддержать предусмотренные кейсом виды просьб: изменение света, температуры и звука, управление шторами и будильником, подготовку ко сну и другие действия из официального перечня.

Для каждой просьбы сервер должен:

1. Определить, что гость хочет изменить.
2. Получить текущее состояние нужного устройства.
3. Рассчитать новое значение и проверить ограничения.
4. Отправить команду.
5. Проверить результат и сформировать ответ гостю.

Например, «на два градуса теплее» означает изменение относительно текущей температуры. Остальные настройки комнаты сохраняются.

Если просьба неоднозначна, выходит за возможности системы или содержит недопустимое значение, сервер должен ответить по правилам кейса. Сообщать об успешном выполнении без подтверждения нельзя.

**Готово, когда:** поддерживаются все 19 видов намерений из кейса, последовательные просьбы учитывают предыдущие изменения, а ошибки не приводят к случайным командам.

### 5. Подключить симулятор комнаты

Реализовать создание сеанса комнаты, передачу расписания, отправку отдельных команд и получение состояния устройств.

Проживания и проверочные просьбы должны использовать предусмотренные организаторами виды сеансов. Начальное состояние берётся по правилам симулятора.

Особое внимание — обрыву связи после отправки команды. Команда могла выполниться, даже если ответ не пришёл. Перед повтором необходимо проверить состояние или журнал, чтобы просьба «сделай теплее» не применилась дважды.

**Готово, когда:** изменения подтверждаются данными симулятора, а при сбое сервер различает подтверждённый результат и неизвестный исход операции.

### 6. Реализовать проверочный маршрут /run

Этот маршрут нужен для автоматической оценки решения организаторами.

Он должен принять запрос с токеном и кодом набора данных, загрузить набор, обработать проживания и просьбы, а затем вернуть результат в установленном формате.

В ответ включаются ссылки на созданные сеансы и ответы на сообщения гостя. Точный состав полей определяется официальной схемой Case2Answers.

Во время прогона сервер должен продолжать отвечать на проверку доступности. Обработку нужно ограничить по времени и числу одновременных операций, чтобы уложиться в ресурсы стенда.

**Готово, когда:** все записи набора обработаны, ответ соответствует схеме, а указанные сеансы содержат фактически выполненные действия.

### 7. Подготовить API для интерфейса

Вместе с Алексеем описать запросы и ответы, необходимые для экранов:

- создание пользовательского сеанса;
- получение данных гостя;
- просмотр подготовленного расписания;
- получение состояния комнаты;
- отправка сообщения и получение результата.

Для каждого запроса указать поля, примеры успешного ответа и возможные ошибки. Документацию сохранить в docs/client-api.md.

Пользовательские сеансы должны быть отделены от сеансов автоматической проверки. Токены сервисов организаторов нельзя передавать в браузер.

**Готово, когда:** Алексей может подключить экраны по документации, а два пользователя не видят и не меняют состояние друг друга.

### 8. Обработать ошибки и ограничения

Предусмотреть ситуации, когда внешний сервис долго отвечает, недоступен, отклоняет запрос или возвращает неожиданные данные.

Нужно ограничить время ожидания и количество повторов, проверять входящие данные и не сохранять секреты в логах.

Если для понимания сообщения используется языковая модель, её ответ также проверяется кодом. Она не должна самостоятельно определять допустимые диапазоны устройств или подтверждать выполнение команды.

**Готово, когда:** сбой одной операции не ломает остальные сеансы, а пользователь получает понятное сообщение без ложного подтверждения успеха.

### 9. Обновить проверки и выложить рабочую версию

После реализации /run убрать из проверки деплоя ожидание ответа 501 — этот ответ относится к стартовой заглушке.

При каждом изменении запускать автоматические тесты. После деплоя выполнять лёгкую проверку доступности сервера. Полную обработку набора с обращениями к внешним сервисам запускать отдельно.

Перед переносом реализации в main проверить приложение локально и на dev-наборе организаторов. Отдельно проверить формат ответа и правильность поведения: соответствие формату ещё не означает, что номер настроен правильно.

**Готово, когда:** тесты проходят, результаты реального прогона зафиксированы, а на стенде работает проверенная версия.

## Что ещё нужно уточнить

В описании /runs и README организаторов обнаружено расхождение относительно работы финального этапа: срока доступа к сеансам и способа передачи результатов. До завершения интеграции нужно выяснить, какой порядок действует, и зафиксировать ответ в документации.

Точные адреса и поля клиентского API необходимо согласовать Николь и Алексею до подключения интерфейса. Пока это проектируемая часть нашего приложения, а не готовый интерфейс организаторов.

## Ограничения стенда

- Python 3.11, 512 МБ оперативной памяти, 1 CPU.
- Зависимости устанавливаются при сборке приложения.
- Во время работы доступ в интернет ограничен сервисами организаторов.
- Локальные файлы могут пропасть при новом деплое.
- start.sh и requirements.txt должны оставаться в корне проекта.
- Секреты доступа хранятся вне исходного кода.
- Временные значения передаются с явным смещением относительно UTC, без обозначения Z.
- Проверочный прогон должен укладываться в отведённое время; в текущем плане учитывается лимит 45 минут.

## Как понять, что решение готово

- [ ] Сервер получает данные нужного гостя и использует только доступную на тот момент историю.
- [ ] Расписание выполняет правила кейса и учитывает ограничения устройств.
- [ ] Команды действительно изменяют состояние симулятора.
- [ ] Поддерживаются все предусмотренные виды просьб.
- [ ] Разные гости и сеансы изолированы друг от друга.
- [ ] Повтор запроса не приводит к повторному изменению по ошибке.
- [ ] /run обрабатывает набор и возвращает результат установленного формата.
- [ ] Интерфейс показывает данные сервера и подтверждённые результаты действий.
- [ ] Ошибки обрабатываются понятно, секреты не раскрываются.
- [ ] Автоматические тесты и проверка на dev-наборе выполнены; результаты и оставшиеся ограничения записаны.
- [ ] Проверенная версия доступна на стенде.
