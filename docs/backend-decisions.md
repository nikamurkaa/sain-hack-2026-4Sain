# Правила работы серверной части

## Что принято для первой реализации

Эти решения позволяют подключать интерфейс и проверять сервер сейчас. Их можно уточнять по результатам проверки и работы команды.

| Ситуация | Поведение |
| --- | --- |
| Нет времени отбоя | Используется 23:00; это техническое значение по умолчанию |
| Нет домашнего часового пояса | Используется пояс отеля |
| Нет температурных предпочтений | 19,5 °C |
| Есть предпочтение прохлады / тепла | 17,5 / 21,5 °C — середины диапазонов правил |
| Нет любимого звука | В ночном расписании звук выключен; просьба включить неопределённый звук требует уточнения |
| Есть любимый звук, нет точных параметров | Громкость 15, таймер 30 минут |
| Нет предпочтения будильника | В расписании свет и звук; обычная команда установки времени сохраняет текущий режим |
| «Теплее» / «прохладнее» без числа | Изменение на 1 °C в пределах устройства |
| «Ярче» / «темнее» без числа | Изменение на 20 процентных пунктов |
| «Тише» без числа | Уменьшение на 10 процентных пунктов |
| Явно указано недопустимое число | Отказ, без изменения состояния |
| «Выключи всё» | Выключить свет и звук; сохранить климат, шторы и будильник |
| «Как дома» | Изменить только подтверждённые домашние настройки |
| «Как вчера» | Использовать явные настройки за предыдущую календарную дату в местном времени текущего проживания |
| Нет данных для «как дома» / «как вчера» | Попросить уточнить настройки |
| «Я проснулся» | Снять будильник и «Не беспокоить», включить свет по утренним привычкам; без данных — 70%, 4000 K. Другие поля менять только при подтверждённой привычке |
| Медицинский вопрос или просьба вне возможностей номера | Отказ без изменения устройств |

## Источники предпочтений

В решение передаются профиль и история только нужного гостя. Сообщения позже времени текущей записи исключаются; завершённое событие учитывается только если оно уже закончилось.

Постоянные предпочтения отделяются от разовых просьб. Подтверждённое поведение в номере важнее общих слов о том, что человеку нравится. Новые фактические настройки заменяют устаревшие. Для каждого извлечённого значения сохраняются источник, время и точная цитата. Код проверяет существование источника и цитаты, допустимость ключа и значения. Если ссылка ошибочна, но точная цитата встречается ровно в одном доступном источнике этого гостя, ссылка исправляется с отметкой source_repaired. Неоднозначное совпадение отклоняется. Смысловое качество извлечения требует отдельной проверки с моделью.

Структурированные значения температуры и любимых треков в профиле имеют приоритет, если заполнены. Для недостающих значений используются история и явно отмеченные значения по умолчанию. Это решение нужно пересмотреть, если организаторы зададут другой порядок приоритета.

## Часовые пояса и расписание

Привычное время сна сначала переводится из домашнего пояса в пояс отеля. При разнице от трёх часов применяется поправка на один час в сторону местного времени. Выбирается подходящее наступление отбоя перед целевым подъёмом. Проверка на пяти dev-проживаниях совпала с эталоном.

Вечерний свет включается за час до отбоя или с момента позднего заселения. Ночные настройки включаются при отбое. Рассвет начинается за 30 минут до подъёма и состоит из трёх ступеней яркости. Звук начинается в контрольной точке через пять минут после отбоя и выключается отдельным шагом: поле таймера симулятора само по себе ничего не выключает.

Поддерживаются правила R1–R8 версии gen-case2-draft-2026-11-14. Изменение текста или состава правил требует проверки реализации; сервер не исполняет произвольные новые правила из текста автоматически.

## Проверочные просьбы и сообщения в интерфейсе

Каждая проверочная просьба получает отдельную комнату с initial_state из набора. Две реплики одной просьбы обрабатываются вместе как уточнение одного действия. Возвращается один итоговый ответ. Расчёт относительных изменений опирается на начальное состояние записи, поэтому повтор не должен накапливать изменения.

В интерфейсе команды используют фактическое состояние комнаты. Повторы одного сообщения защищены Idempotency-Key. Если ответ потерялся или несколько действий выполнились частично, сервер не сообщает об успехе без проверки.

## Ограничения и вопросы организаторам

- В README описан финальный вызов /run, а действующая документация /runs говорит о финальном доступе без пакетной сдачи. Реализован контракт /run из README и отдельный клиентский API для dev-демонстрации. Финальный вход с токеном final в клиентский API пока не реализован: нужны точные правила выдачи такого доступа.
- Создание dev-прогона командным токеном выполняется с телом {"case": 2}. Поле stage сервис принимает только от администратора. Проверено реальным запросом.
- Клиентские сеансы хранятся в памяти и исчезают при перезапуске. Это подходит для хакатонной демонстрации, но не является постоянным хранилищем гостевых настроек.
- Для демонстрации нет самостоятельной регистрации и входа гостей: временный сеанс создаёт участник команды из доверенной среды.
- Ограничитель запросов модели действует внутри одного процесса. Лимит команды общий с другими инструментами, поэтому параллельная работа участников всё равно может вызвать 429.
- Повторные операции не являются транзакцией. Неудачное выполнение может оставить часть изменений; клиент получает ошибку и должен обновить состояние.
- Полный прогон с моделью ещё не завершён. На сохранённых ответах подтверждены 4 из 5 профилей и 13 из 14 доступных просьб. Найден пропуск предпочтений; подробнее — в verification.md.
- Одновременно выполняются не более трёх записей набора. Одинаковые запросы предпочтений объединяются; порядок результата сохраняется.
- Известные названия режимов будильника light_only и sound_only преобразуются в light и sound. Неизвестные режимы отклоняются.
