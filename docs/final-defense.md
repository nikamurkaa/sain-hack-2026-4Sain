# Приёмка финальной защиты

Кейс №2, §1 и §10, требует заселения от имени одного финального пользователя, персонального сценария и просьб жюри. Инструкция предусматривает, что после ответа на финальный POST /run сервер команды продолжает работать, а клиент запускается на компьютере организаторов.

## Официальные возможности

Проверена опубликованная [спецификация API](https://github.com/sainorg/sain-hackathon-docs/blob/main/contracts/openapi.json), blob `e745eb7e8a1cea596bf2558f6700d7757c9b4ab5`, и разъяснение команды о HTTP 409.

| Метод | Полномочия и следствие |
| --- | --- |
| GET /case/2/getData | Токен закреплён за набором и окном доступа. Для final срок доступа ограничен окном токена. |
| POST /runs | Команда может создать dev-прогон с телом {"case":2}. Выбор stage, restart и test закреплён за организатором. |
| GET /runs/{run_id} и evaluation | Информация о прогоне и расчёте, права на запись не выдаются. |
| POST /room/session | Комната привязана к команде, прогону и записи. Повтор возвращает существующую комнату. Схема принимает record_id, kind и run_id. Полей импорта профиля и клонирования между наборами нет. |
| POST /room/{id}/action и scenario | Изменения только в своём прогоне, после сохранения ответа закрыты. |
| GET /room/{id}/state, log, /room/devices | Чтение состояния на виртуальное время, журнала и каталога в пределах доступных прав. |
| validate и medcheck | Проверяют данные, ссылки и формулировки. Сеанс для управления гостем не создают. |

В опубликованном контракте нет операции переноса финального гостя в доступную для записи комнату. При подготовке финала следует уточнить: «Каким официальным вызовом и каким контекстом доступа команда может выполнить просьбу жюри для record_id финального заезда после сохранения /run? Если такого механизма нет, допускается ли отдельный показ управления в явно обозначенном dev-номере?»

## Что можно предъявить жюри

| Требование | Статус | Доказательство и граница |
| --- | --- | --- |
| Обработка финального набора, подготовка сценария, итоговый JSON | Выполнено в локальном контрактном тесте | POST /run с фазой final, один заезд, журнал симулятора и исходная схема ответа. |
| Просмотр настоящего гостя и его расписания спустя несколько часов | Выполнено на уровне API | Через 4 часа открывается новый клиентский доступ. Профиль и расписание доступны при 403 от upstream. |
| Просмотр состояния на выбранное время | Частично | Зависит от действительности прав чтения. Кеш помечен отдельно, со временем подтверждения. |
| Просьбы, контекст, изменение устройств | Выполнено для dev на уровне API | Отдельные /runs и /room/session. Команда проверяется по состоянию симулятора. Повтор ключа не создаёт второго действия. |
| Просьбы именно финальному заезду после сохранения ответа | Блокируется официальным контрактом | 409 на запись. Допуск демонстрации в dev как замены этого элемента жюри не подтверждён. |
| Адаптивные экраны, голос с микрофона на компьютере жюри | Частично | Серверный контракт и STT готовы. Нужны интеграция Figma-клиента и приёмка на устройстве. |
| Показ после перезапуска контейнера | Ограничение реализации | Подготовленный профиль хранится в одном процессе. После рестарта требуется новая разрешённая финальная подготовка организаторами. |

Для выступления сначала открыть «Финальный гость», показать профиль и персональный вечер, ночь, утро. Затем отдельно открыть «Демонстрационный номер», назвать источник вслух и попросить сделать прохладнее. Показывать значение только после ответа симулятора. Официальный dev-прогон для защиты запускается командой в период показа, с действующими правами и доступной квотой.

## Проверка ветки

Команды из корня: `python -m pytest -q` и `python -m scripts.check_offline`. Локальные проверки с FakeModel и MockTransport. Тесты tests/test_defense.py проходят реальный HTTP-путь приложения, проверяют отложенный вход, идентичные record_id разных прогонов, отдельные токены, 403, 409, 429, срок upstream, повтор клиентского запроса и восстановление истории. Проверка в живом окружении организаторов в этот результат не входит.
