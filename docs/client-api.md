# Подключение интерфейса

> **Обновление 24.11.2026:** разделы ниже частично описывают исходный конкурсный STAND. В автономном REHEARSAL теперь реализовано локальное SQLite-восстановление гостевых сеансов, истории и подтверждённых настроек после рестарта; исходный токен нужно повторно ввести в браузере. LIVE и официальный STAND этой гарантии не имеют. Актуальные ограничения: [technical handoff](release/FINAL_TECHNICAL_HANDOFF.md).


Стенд: https://team25.hack.be-healthy.tech. Локально: http://127.0.0.1:8000.
Точные поля и схемы ответов: `/docs` и `/openapi.json`.

## Пример для вёрстки

Четыре файла описывают одно вымышленное проживание. Их можно импортировать в локальный клиент как ответы API без токенов и запросов на стенд.

| Запрос | Пример ответа |
| --- | --- |
| `GET /api/v1/guest` | [Гость и предпочтения](examples/room/guest.json) |
| `GET /api/v1/scenario` | [Расписание на ночь](examples/room/scenario.json) |
| `GET /api/v1/state` | [Комната до просьбы, 22 °C](examples/room/state.json) |
| `POST /api/v1/messages` | [Ответ и состояние после просьбы, 21 °C](examples/room/message.json) |

При открытии экрана покажите гостя, расписание и текущие настройки. Для кнопки отправки используйте такой пример тела запроса:

```json
{"text":"Сделай попрохладнее","at":"2026-11-12T20:00:00+03:00"}
```

После отправки покажите `reply.text` и обновите карточки из `state` ответа. Температура меняется с 22 на 21 °C, остальные настройки сохраняются. Для настоящего API порядок получения токена и передачи `Idempotency-Key` приведён ниже.

## Сеанс

1. Участник команды из терминала создаёт сеанс: `POST /api/v1/sessions`, `Authorization: Bearer <HACK_TEAM_TOKEN>`.
2. Сервер готовит номер и возвращает `session_token`, `at`, `until` и срок действия.
3. Интерфейс получает только `session_token` и передаёт его как `Authorization: Bearer <session_token>`.

Тело создания:

```json
{"dataset_code":"case2-dev-v1","stay_id":"идентификатор проживания из набора"}
```

Ключ модели и командный токен в браузер не передаём. Токен сеанса храним в памяти приложения, не в URL или аналитике. Токен просмотра final действует 30 минут от подключения. Dev-сеанс доступен до срока официального прогона, максимум 45 минут с его создания. Доступны до 100 сообщений на разговор и до восьми одновременных клиентских токенов. При перезапуске сервера они исчезают.

## Маршруты

| Запрос | Результат |
| --- | --- |
| `GET /api/v1/session` | Источник, доступные действия, статус последней связи, оставшееся время и история разговора |
| `GET /api/v1/prepared` | Подготовленные гость и сценарий, последнее подтверждение этого подключения или null |
| `GET /api/v1/guest` | Гость, поля профиля сна, проживание, предпочтения и источники |
| `GET /api/v1/catalog` | Устройства, диапазоны и звуки |
| `GET /api/v1/scenario` | Расписание в `steps` |
| `GET /api/v1/state` | Подтверждённое состояние комнаты |
| `GET /api/v1/state?at=…` | Состояние в указанное время проживания: read-only virtual preview, не подтверждает проблему другой операции |
| `GET /api/v1/reconciliation?operation_id=…` | Авторизованная сверка именно проблемной операции на её `attempted_at`; только чтение от симулятора, без повторного POST |
| `POST /api/v1/messages` | Ответ на просьбу и новое состояние |
| `POST /api/v1/transcriptions` | Аудиозапись → распознанный текст |
| `DELETE /api/v1/session` | Закрытие сеанса, HTTP 204 |

## Сообщения

Для `POST /api/v1/messages` добавьте `Idempotency-Key` — уникальный UUID сообщения. При повторе после обрыва связи отправляйте тот же ключ и тело.

```json
{"text":"Сделай на два градуса теплее","at":"2026-11-12T20:05:00+03:00"}
```

Дата выше условная: используйте виртуальное время между `at` и `until` из сеанса. Новая команда не может быть раньше предыдущей. Нужен явный UTC-offset, обозначение `Z` не принимается. Для query-параметра времени используйте `URLSearchParams`, чтобы правильно закодировать `+`.

Ответ содержит `reply` (текст и `response_class`) и `state`. При `done` показывайте подтверждённое состояние, при `refused` — отказ или уточнение. До ответа показывайте ожидание. Просмотр будущего состояния через GET не меняет время сообщений.

## Ошибки и подключение

| HTTP | Действие |
| --- | --- |
| 401 | Получить новый сеанс: токен отсутствует или истёк |
| 403 | Проверить доступ к служебному действию или внешнему сервису |
| 409 | Показать сообщение о конфликте ключа/времени или неизвестном результате; обновить состояние |
| 422 | Исправить запрос; подробности в `detail` |
| 429 | Достигнут лимит сеансов или сообщений |
| 502 / 503 / 504 | Показать ошибку внешнего сервиса и обновить состояние |

Ошибки приложения содержат `status`, `code`, `message`. При `ACTION_PARTIAL`, `ACTION_UNCERTAIN` и `ACTION_CONFLICT` добавляются `operation_id`, `confirmed_devices` и серверный `attempted_at`. Простой GET `/state` может относиться к старому `session.at` и **не** подтверждает эффект в другой момент. Вызывайте только `GET /api/v1/reconciliation?operation_id=…` (тот же guest bearer), проверяйте operation_id/status/confirmed_devices/UTC-момент `attempted_at` и `snapshot.at`. При неудаче/просроченном снимке сохраняйте состояние `stale`, блокируйте новые действия, не повторяйте POST. Только после подтверждённого снимка используйте `next_action_at` из /session или ответа сверки для новой сознательной команды. Обычный `GET /state?at=` остаётся виртуальным read-only просмотром и не снимает блокировку.

Интерфейс размещаем на том же домене или подключаем через прокси dev-сервера для `/api`. CORS для произвольных сайтов не включён. Выдача временных сеансов — текущий способ демонстрации; вход реальных гостей пока не реализован.


## Подготовленный пользователь финального показа

Служебный клиент команды открывает финального гостя телом `{"source":"final"}`. Для демонстрационного управления команда открывает отдельное проживание через `{"source":"dev","dataset_code":"case2-dev-v1","stay_id":"<dev-record-id>"}`. Браузер получает только выданный токен. Открытие нового dev-сеанса создаёт новый официальный прогон.

**Начало и восстановление экрана.** С тем же клиентским токеном запросите `GET /api/v1/session`. Он возвращает поля создания сеанса (кроме токена) и массив `history` с виртуальным временем, текстом просьбы и подтверждённым ответом. Список содержит завершённые обмены. После 401 для локального `SESSION_EXPIRED` выдаётся новый токен. Если dev-прогон закончился, новый dev-разговор начинается с пустой историей. Ошибки и истечение токена не запускают автоматическую смену гостя.

| Поле | Как использует интерфейс |
| --- | --- |
| `source` | `final` — «Финальный гость · просмотр». `dev` — «Демонстрационный номер · управление». |
| `mode` | Значение `simulator` сохранено для совместимости. Источник определяется по `source`. |
| `read_only`, `can_send_requests`, `actions` | Кнопка отправки требует `message`, микрофон — `transcription`. После 409 обновить возможности сеанса. |
| `connection_status` | Последняя попытка взаимодействия: `unchecked`, `available`, `rate_limited`, `unavailable` или `access_ended`. После 429 показать ожидание. После неопределённого результата сначала перечитать состояние. |
| `expires_in`, `at`, `until` | Первое — оставшиеся реальные секунды доступа браузера. `at` — только последняя полностью успешная операция; `until` — конец проживания. |
| `next_action_at`, `reconciliation_required`, `pending_action` | Монотонная временная граница новых действий; безопасная блокировка до сверки; операция, которую можно восстановить после reconnect с тем же гостевым токеном. Новое действие ранее `next_action_at` отвергается даже при valid session. |

**Подготовленные и живые данные.** Сначала загрузите `/prepared`: `provenance: "prepared"`, `guest`, `scenario.steps`, `last_confirmed`. Это доступно даже при ошибке внешнего API. Затем отдельно вызовите `GET /state?at=…`. Только успешный ответ этого метода или подтверждённый ответ на команду даёт состояние от симулятора. На ошибке покажите «Живое состояние недоступно». Если есть `last_confirmed`, подпишите «Последнее подтверждение на [виртуальное время]». До первого подтверждения поле равно null. Прогноз по расписанию и начальные настройки не являются подтверждением. При смене токена сбросьте карточки и чат предыдущего гостя, отмените его запросы и игнорируйте запоздалые ответы.

**Срок хранения.** После завершения финального запроса сервер держит один подготовленный профиль до следующей финальной подготовки или остановки процесса. Токен просмотра выдаётся в момент подключения, в том числе спустя несколько часов. Повторная выдача не меняет полномочия источника. `/prepared` и `/session` не вызывают организаторов. [Матрица и ограничения защиты](final-defense.md).

## Контекст диалога

Сервер учитывает предыдущие просьбы и ответы в текущем сеансе, включая успешные команды. «Ещё немного» интерпретируется по истории. Повтор с тем же ключом не добавляет новую реплику и не выполняет действие повторно. Сохраняйте один сеанс на разговор.

## Голос

Записывайте микрофон через `MediaRecorder` в HTTPS или на localhost. Проверяйте доступность API и MIME через `MediaRecorder.isTypeSupported`; при отказе в доступе оставляйте текстовый ввод.

Отправка **самого Blob в теле**, без JSON и без FormData:

```javascript
const response = await fetch('/api/v1/transcriptions', {
  method: 'POST',
  headers: {
    Authorization: `Bearer ${sessionToken}`,
    'Content-Type': recording.type,
  },
  body: recording,
});
if (!response.ok) throw new Error('Не удалось распознать речь');
const { text } = await response.json();
// Показать text в поле чата; отправлять через /messages с новым Idempotency-Key.
```

Ответ: `{"text":"Сделай попрохладнее."}`. Само распознавание не меняет устройства. Лимит самого файла — 5 000 000 байт включительно. Сервер считает байты в потоке, в том числе при отсутствии Content-Length. Для демонстрации ограничьте запись 30 секундами. Сервер не сохраняет аудио в файлы и передаёт его в речевую модель прокси организаторов с тем же серверным ключом.

### Форматы записи

| Content-Type тела браузера | Расширение в multipart |
| --- | --- |
| audio/webm (в том числе с параметром codecs) | webm |
| audio/mpeg, audio/mp3 | mp3 |
| audio/wav, audio/x-wav | wav |
| audio/mp4, audio/m4a, audio/x-m4a (аудиодорожка M4A) | m4a |
| audio/ogg | ogg |
| audio/flac, audio/x-flac | flac |

Бэкенд отправляет поле `file` с именем `request.<расширение>` и корректным MIME на `LLM_BASE_URL/audio/transcriptions`. Остальные поля multipart — `model=gpt-transcribe`, `language=ru`, `response_format=json`. Используется серверный `LLM_API_KEY`. На стенде работает один процесс с общим ограничителем чата и голоса. В скользящем окне 60 секунд допускается до 10 стартов STT. Каждый расходует также слот общего лимита 30 в минуту. Вызовы вне данного процесса учитывает прокси.

| HTTP и code | Что показать или сделать |
| --- | --- |
| 402 SPEECH_BUDGET | Дневной бюджет STT ($3) исчерпан. Предложить текстовый ввод до 00:00 МСК. |
| 413 AUDIO_TOO_LARGE | Укоротить или сжать запись. Код одинаков при локальном отказе и ответе прокси. |
| 429 SPEECH_LIMIT | Подождать минуту. Автоматический повтор записи не нужен. |
| 429 SPEECH_BUSY | Дождаться окончания текущего распознавания. |
| 415 AUDIO_TYPE / 422 AUDIO_EMPTY, INVALID_AUDIO | Выбрать поддерживаемый формат или повторить запись. |
| 502 / 503 / 504 | Оставить текстовый ввод доступным. |

После получения `text` браузер показывает его для проверки. Только подтверждение гостя отправляет обычный `POST /api/v1/messages` с виртуальным временем и ключом идемпотентности. Это одна и та же операция для клавиатуры и микрофона.

### Озвучивание на защите

Официальный TTS позволяет по запросу гостя озвучить уже подтверждённый `reply.text` через серверный вызов `/audio/speech` с `tts-1`. Максимум 4096 символов, результат MP3, отдельные $3 в сутки и 10 запросов в минуту при общем ограничении ключа 30. Для финала потребуются отдельный счётчик, кнопка воспроизведения и проверка браузера. Текущая версия возвращает текст.


## Отмена server task при потерянном ответе — MR-NEW-04
Если клиент получил HTTP500/network abort/timeout от POST, нельзя считать операцию неисполненной и повторять с новым Idempotency-Key. Оставаясь в той же гостевой сессии, выполните `GET /api/v1/session`: если `reconciliation_required=true` и `pending_action` содержит `operation_id`, `attempted_at`, `confirmed_devices`, `code=ACTION_UNCERTAIN`, откройте сообщение с отсутствием подтверждения и предложите только `GET /api/v1/reconciliation?operation_id=...`. Никакой GET не отправляет новый upstream POST. Пока не подтверждён снимок именно для исходной операции на её UTC instant, блокируйте новые изменяющие команды, даже при непустом поле текста. Успешная сверка показывает наблюдённое состояние, но **не** доказывает атомарность или exactly-once. Даже после сверки новые commands используют `next_action_at>=mutation_floor`, а не старое `session.at`. Повтор прежнего ключа с тем же телом возвращает кешированный uncertain 409, но не изменяет комнату; иной payload — 409 `IDEMPOTENCY_CONFLICT`. При ошибке GET оставьте stale и pending. После перезапуска процесса старый guest token не восстанавливается: новая синтетическая сессия не является продолжением старой.


## MR-NEW-06 — контракт достоверно отклонённого POST

Только два POST маршрута — `/api/v1/messages`, `/api/v1/devices` — возвращают дополнительный **`X-Sain-Rejection-Class: prehandler`** на FastAPI RequestValidationError HTTP422 (Pydantic отбрасывает запрос до запуска обработчика) и **`X-Sain-Rejection-Class: domain`** на HTTP422 безопасных ServiceError `INVALID_TIME` (оба) и `INVALID_VALUE` (/devices). Ровно этот allowlist проходит локальный reverse proxy `frontend/serve.py`. Сам HTTP422, произвольная структура JSON, другие 4xx/5xx, `ACTION_UNCERTAIN` и потерянный HTTP response **не** позволяют снять блокировку. При сертифицированном отказе React сохраняет draft и отдельным GET /session проверяет, что **нет другой** незавершённой операции; только тогда позволяет осознанно отредактировать и заново отправить запрос с новым Idempotency-Key. При неизвестном исходе действуют имеющиеся `pending_action`/`GET reconciliation`/mutation_floor и запрет автоматического POST. Кнопка «Повторить» в mobile/desktop не предлагается в состоянии blocked и не выполняет заведомо запрещённое действие.
